## 1 · MAME: política de versión (afecta ADR-0005, ya escrito — este es un AJUSTE)

**Decisión:** MAME vanilla **0.288 o superior**, con una regla no negociable:
> El Mac (desarrollo) y el gabinete (producción) corren **exactamente la misma
> versión** de MAME, y esa versión es **igual o superior** a la del romset (0.288).

**Por qué el ajuste (no "0.288 o superior" a secas):**
MAME es retrocompatible hacia atrás, NO hacia adelante. Un emulador 0.291 corre
romsets 0.288; un emulador 0.288 NO corre romsets 0.291. Sin la regla de "misma
versión en ambas máquinas", un Homebrew que se auto-actualiza en el Mac reintroduce
el bug de dos `-listxml` distintos — el mismo problema que ADR-0005 existe para evitar.

**Consecuencia nueva que esto agrega:** hay que FIJAR la versión de MAME (evitar
auto-update de Homebrew) y actualizar deliberadamente en ambas máquinas a la vez.

**Estado:** ✅ **Cerrado.** Está en `spec/decisions/0005-runtime-mame-vanilla.md`
(`status: accepted`), con la regla de "misma versión en ambas máquinas" y el
punto de fijar la versión para evitar auto-update.

## 2 · Transporte de datos ricos: JSON externo, no embebido (ADR-0001)

**Decisión:** Los datos ricos (`mags`, `cheats`, `review`) NO van en el
`metadata.pegasus.txt`. Van en un archivo `data.json` aparte, junto a los assets
del juego.

**Evidencia que la respalda (experimentos corridos hoy):**
- `game.extra.X` es SIEMPRE una lista (`QStringList` de Qt), nunca un string simple.
  No es `Array` de JS (`Array.isArray()` da `false`), pero se accede por índice.
- Las claves con guión se preservan literales: `extra["con-guion"]`.
- QML SÍ puede leer un archivo `.json` externo con `XMLHttpRequest` + ruta `file://`
  y parsearlo con `JSON.parse()` — VERIFICADO, funciona, incluso con estructura de
  dos niveles anidados.

**Por qué C y no A/B:** el criterio rector es que agregar un scan de revista seis
meses después cueste lo mismo que agregar una carátula (dropear/editar un archivo,
sin tocar el metadata central ni el código). A (JSON embebido en `x-`) rompe esto
porque editar JSON minificado a mano en el metadata es doloroso y un error de sintaxis
rompe el campo entero en silencio. B (listas paralelas) no soporta la estructura de
dos niveles de los combos.

**Estado:** ✅ **Cerrado.** Está en `spec/decisions/0001-transporte-datos-ricos.md`
(`status: accepted`).

## 3 · Formato de páginas de revista: IMÁGENES, no PDF

**Decisión:** Las páginas escaneadas de revista se guardan como imágenes
(`.jpg`/`.png`), una por página. NUNCA como PDF embebido en el theme.

**Por qué (verificado, no supuesto):**
- Pegasus está construido con Qt 5.15, y sus dependencias declaradas de build son
  únicamente: QML/QtQuick2, Multimedia, SVG, SQL (SQLite). **PDF no está.**
- Investigación confirmó: no hay QtWebView ni QtWebEngine en los binarios oficiales
  de Pegasus. El único soporte de "rich text" en QML es un subconjunto de HTML 3.2/4
  sin CSS de layout ni JS — inútil para reusar el mockup React.
- Mostrar PDF en Qt5/QML requeriría Poppler-Qt5 + un plugin QML de terceros
  (ej. Poppler-QML-plugin) compilado aparte e integrado al binario de Pegasus —
  fuera de alcance, no soportado por builds oficiales.
- Pegasus está congelado desde octubre 2024 (última release), sin desarrollo activo:
  no va a sumar soporte de PDF.

**Consecuencia para el pipeline (futuro):** ATTRACT (o el subsistema de revistas,
ver punto 6) tiene que CONVERTIR cada PDF de revista a imágenes por página como
parte de la ingesta. Esto es trabajo nuevo, no automático.

**Estado:** 🟡 **Slot reservado: ADR-0007.** Sin escribir. Si al redactar el 0008
te queda claro que es el mismo tema, anexalo ahí y liberá el número (los números
no se reutilizan: quedaría 0007 como "no usado, ver 0008").

**Contraprueba archivada:** `themes/experimentos/pdf-qtquick.qml` intenta
`import QtQuick.Pdf` contra Pegasus. Si algún día carga, este punto se reabre.
El resultado observado todavía no está anotado en ese archivo.

## 5 · Modelo de datos de revistas: entidad de primera clase (el hallazgo grande de hoy)

**El problema que lo origina:** una revista NO pertenece a un solo juego. Una misma
revista (ej. PC Juegos Nº32) puede tener notas de varios juegos en páginas distintas
(Mario en la página 15, Day of the Tentacle en las 16-20). Si las páginas se guardan
"dentro" de cada juego, la revista se duplica tantas veces como juegos cubra.

**Decisión:** las revistas son una **entidad separada** de los juegos, con su propia
carpeta e identidad. Los juegos la REFERENCIAN, no la contienen. Relación
muchos-a-muchos: una revista cubre muchos juegos, un juego aparece en muchas revistas.

**Requisito adicional (dado por vos) que definió la forma final:** el usuario tiene
que poder abrir el visor DESDE la página del juego (entra directo en la nota) pero
LUEGO poder hojear la revista COMPLETA, no solo esa nota — la nota es la puerta de
entrada, no un límite.

**Estructura de carpetas:**
```
media/
├─ _magazines/                    ← las revistas, cada una UNA sola vez
│  └─ pcjuegos-32/
│     ├─ magazine.json            ← el contrato completo (ver abajo)
│     ├─ cover.jpg
│     ├─ p001.jpg ... p100.jpg    ← TODAS las páginas del escaneo, en orden
│
├─ dino/                          ← un juego (carpeta = SET de MAME, no título)
│  ├─ boxFront.jpg                ← assets nativos de Pegasus (auto-descubiertos)
│  ├─ video.mp4
│  └─ data.json                   ← REFERENCIA a revistas, no las contiene
```

**Formato de `magazine.json`:**
```json
{
  "name": "PC JUEGOS",
  "issue": "32",
  "year": 1993,
  "color": "#7d2fb8",
  "cover": "cover.jpg",
  "pages": ["p001.jpg", "p002.jpg", "...", "p100.jpg"],
  "articles": [
    { "game": "mario", "title": "Super Mario",        "startPage": 15, "pages": [15] },
    { "game": "dott",  "title": "Day of the Tentacle", "startPage": 16, "pages": [16,17,18,19,20] }
  ]
}
```

- `pages` (nivel revista) = TODAS las páginas del escaneo, en orden → lo que el
  visor recorre cuando el usuario hojea la revista entera.
- `articles[].pages` = lista de números SUELTOS (no rango) porque una nota puede
  estar en páginas no consecutivas (cortada por publicidad, etc.).
- `articles[].startPage` = dónde ABRE el visor cuando se entra desde ese juego
  (explícito, no inferido, para que el pipeline no tenga que adivinar).

**Formato de `data.json` de un juego (referencia, no copia):**
```json
{ "mags": [ { "ref": "pcjuegos-32" } ] }
```
El juego NO repite sus páginas — ya están en `magazine.json → articles[].pages`
buscando por `game == "<set>"`. Una sola fuente de verdad.

**Por qué esto es mejor:** cero duplicación de escaneos; conseguir una revista nueva
enriquece automáticamente a TODOS los juegos que ya la referencian; permite (a
futuro) una sección "explorar revistas" en el frontend, porque la revista existe
como entidad navegable.

**Verificación pendiente (no corrida):** que el theme pueda encadenar DOS lecturas
de JSON — leer el `data.json` del juego, sacar el `ref`, y cargar el
`magazine.json` correspondiente. Se probó UN JSON externo (funciona); falta probar
la cadena de dos.

**Estado:** 🔴 **Slot reservado: ADR-0008 · Modelo de datos de revistas: entidad
de primera clase.** Sin escribir — es la decisión más grande de la sesión y la
primera que toca redactar.

**El contrato ya está encarnado en fixtures** (`fixtures/arcade/media/`), así que
el ADR se escribe contra algo que existe, no contra un ejemplo del chat:
`_magazines/micromania-16/` con `magazine.json`, `dino/data.json` referenciándola
por `ref`, y `sf2ce/data.json` con un `ref` colgado a propósito para el caso de
degradación. Ver `_magazines/README.md`.

## 6 · Frontera del sistema: ATTRACT consume revistas, no las produce

**Decisión:** la GENERACIÓN de `magazine.json` (escanear la revista, hacer OCR,
mapear qué juego está en qué página) es responsabilidad de un **subsistema aparte,
futuro, fuera del alcance actual de ATTRACT**.

ATTRACT es **consumidor** del contrato, no productor:
- ATTRACT SÍ es dueño de: el FORMATO de `magazine.json` (el contrato), leerlo,
  resolver el `ref`, el visor que lo muestra, la degradación cuando no existe.
- ATTRACT NO es dueño de: escanear, hacer OCR, decidir en qué página está cada
  nota. Eso lo hace un humano hoy, y potencialmente un subsistema mañana.

**Por qué esto importa (más que "lo pateamos para después"):** define un límite de
sistema real. Consecuencia práctica: ATTRACT se puede desarrollar y testear ENTERO
sin que el subsistema de revistas exista. Alcanza con escribir un `magazine.json` a
mano como fixture — el visor no sabe ni le importa quién lo generó, solo que respete
el contrato.

**Estado:** 🔴 **Slot reservado: ADR-0009 · Frontera del sistema: producción vs.
consumo de metadata de revistas.** Sin escribir. Es corto — casi un párrafo — pero
vale la pena que exista por separado porque es un principio de diseño, no un
detalle de formato.

## 7 · Identidad de assets: por SET de MAME, no por título (reafirmado, ya estaba)

Todo lo anterior asume esto, que ya estaba en tu convención pero vale la pena
resaltarlo porque el modelo de revistas lo vuelve todavía más central:

- Carpeta de juego = `media/<set>/` (ej. `media/dino/`), NUNCA el título
  (`Cadillacs and Dinosaurs/` rompe en Windows por el `:` — ni siquiera aplica acá,
  pero el principio es el mismo: título ≠ identidad).
- Carpeta de revista = `media/_magazines/<revista>-<numero>/` (ej. `pcjuegos-32`),
  con el mismo criterio: un identificador estable, no el nombre bonito (que vive
  DENTRO del `magazine.json` como campo `name`).
